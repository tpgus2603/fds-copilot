# 00. 프로젝트 헌장 (Project Charter)

## 1. 배경과 문제 정의

카드 FDS(Fraud Detection System)는 보통 두 단계로 운영됩니다.

1. **1차 탐지**: 규칙이나 모델이 거래를 평가해 의심 거래를 선별합니다.
2. **조사**: 조사역이 선별된 거래마다 증거를 모으고 판단합니다. 해당 카드의 평소 이용 패턴, 가맹점 특성, 거래 위치와 시간을 확인하고, 결과를 기록해 사기 확정 또는 정상 종결을 결정합니다.

1차 탐지는 자동화되어 있지만, 조사 단계는 여러 화면을 오가며 조회하고 비교하는 수작업이 많습니다. 또한 조사 경로가 정해져 있지 않습니다. 다음에 무엇을 확인할지가 앞선 확인 결과에 따라 달라집니다. 예를 들어 고액 거래라면 평소 금액 분포를 먼저 확인하고, 이용 지역이 평소와 다르면 직전 거래와의 거리와 이동 속도를 추가로 확인합니다.

이 프로젝트는 **조사 단계**를 다룹니다. 탐지 이후 조사역이 수행하는 증거 수집, 비교, 기록을 AI 에이전트가 보조하고, 판단은 사람이 내리는 시스템을 만듭니다.

## 2. 프로젝트 정의

**FDS 조사 코파일럿**

```
규칙 탐지 → 조사 케이스 생성 → 기본 증거 자동 수집 → 필요한 추가 조회
        → 근거가 연결된 보고서 → 조사역 검토 → 종결 또는 추가 조사 요청
```

1. 규칙 엔진이 거래를 1차 탐지해 조사 케이스를 만듭니다.
2. AI 에이전트가 MCP 툴(거래 이력 조회, 가맹점·업종 지표 조회, 지리적 이상치 계산)을 상황에 맞게 골라 호출하며 증거를 모읍니다.
3. 에이전트는 의심 근거, 반대 근거, 정보 부족을 구분한 보고서를 작성합니다. 보고서의 모든 주장은 툴 결과의 근거 ID에 연결됩니다.
4. 조사역이 보고서와 툴 호출 기록을 검토해 케이스를 종결하거나 추가 조사를 요청합니다.

### 2.1 범위

| 포함 | 내용 |
|---|---|
| 1차 탐지 | 설명 가능한 규칙 기반 탐지 (고액, 심야, 단시간 연속 거래, 원거리 등) |
| 조사 케이스 관리 | 케이스 상태 전이, 조사역 검토 이력 |
| 증거 조회 툴 | 읽기 전용 MCP 툴 3종 |
| 조사 에이전트 | Claude tool use 기반의 제한된 조사 루프와 보고서 생성 |
| 검토 화면 | 케이스 목록, 툴 호출 타임라인, 근거가 연결된 보고서, 종결 처리 |
| 평가 | 고정 자동화 대비 코파일럿의 효과를 비교하는 실험 |

### 2.2 범위 밖 (Non-goals)

- 사기 탐지 모델의 정확도 향상 (1차 탐지는 규칙으로 충분히 단순하게 유지합니다)
- 실시간 승인 경로(authorization path)에서의 거래 차단
- AI의 사기 확정 판정 (에이전트는 권고만 하고, 판단은 항상 사람이 내립니다)
- 중복 알림 묶기, 조사 결과를 활용한 룰 자동 개선 (후속 범위)

## 3. 접근 방식과 근거

### 3.1 왜 에이전트인가

조사 업무는 확인할 항목과 순서가 앞선 결과에 따라 달라지는 조건부 탐색입니다. 이 구조는 "추론 → 툴 호출 → 결과 관찰"을 반복하는 ReAct 루프와 대응됩니다. 반면 모든 케이스에 같은 조회를 실행하는 고정 파이프라인은 단순하고 예측 가능하지만, 불필요한 조회가 늘거나 필요한 추가 조회를 놓칠 수 있습니다.

다만 **에이전트가 고정 자동화보다 실제로 나은지는 아직 가설입니다.** 이 프로젝트는 같은 데이터와 권한에서 세 가지 방식을 비교해 이 가설을 검증합니다(5절).

### 3.2 왜 사람이 최종 판단하는가 (Human-in-the-loop)

- 사기 확정은 고객의 카드 정지, 이의 제기, 손실 부담으로 이어지는 결정이므로 책임 주체가 분명해야 합니다.
- 생성형 AI의 출력은 비결정적이고 틀릴 수 있습니다. 따라서 에이전트의 역할을 "근거를 모아 정리하는 것"으로 제한하고, 근거와 결론을 사람이 대조할 수 있게 만듭니다.

### 3.3 왜 해석 가능한 데이터인가

보고서의 가치는 "왜 의심스러운가"를 구체적인 값으로 설명하는 데 있습니다. Sparkov 시뮬레이션 데이터는 가맹점명, 업종, 고객과 가맹점 좌표, 거래 시각이 원래 형태로 있어 "평소 평균 금액의 8배", "직전 거래 지점에서 1,200km" 같은 문장을 실제 값에 근거해 쓸 수 있습니다(상세는 `01_dataset_spec.md`).

## 4. 설계 원칙

| 원칙 | 내용 |
|---|---|
| 사람의 최종 결정 | 에이전트는 판정하지 않고 근거와 권고만 제시합니다. |
| 최소 권한 | 툴 서버는 읽기 전용 DB 계정만 사용합니다. 업무 상태 변경은 도메인 백엔드만 수행합니다. |
| 근거 추적성 | 수치는 코드가 계산하고, 툴 결과에 기준 시점, 조회 기간, 표본 수, 근거 ID를 담습니다. 보고서의 주장은 근거 ID에 연결됩니다. |
| 시점 통제 | 조사 대상 거래 시점 이후의 데이터와 대상 거래 자체는 비교 집계에서 제외합니다. |
| 라벨 격리 | 정답 라벨(`is_fraud`)은 조사 경로에 노출하지 않고 평가에만 사용합니다. |
| 실패의 명시 | 빈 이력과 조회 실패를 구분합니다. 근거가 불충분하면 보고서를 만들지 않고 "조사 미완료"로 남깁니다. |
| 개인정보 최소화 | 카드 원번호는 저장하거나 모델에 보내지 않고 토큰으로 대체합니다. |

## 5. 성공 기준

**기능**
- 규칙 탐지부터 조사역 종결까지 전체 흐름이 로컬 환경에서 한 번에 실행됩니다.
- 케이스 성격에 따라 에이전트가 서로 다른 툴 조합이나 순서를 선택하는 사례를 2개 이상 재현합니다.
- 보고서의 모든 주장이 툴 결과의 근거 ID에 연결되고, 보고서의 수치가 툴 결과와 일치하는지 자동으로 검증됩니다.
- 툴 조회 실패나 호출 상한 도달 시 케이스가 "조사 미완료"로 남습니다.

**평가** (같은 데이터와 권한에서 비교)

| 방식 | 내용 |
|---|---|
| A. 수동 조사 | 조사역이 조회 화면으로 직접 확인하고 기록 |
| B. 고정 자동화 | 모든 케이스에 같은 조회를 실행하고 템플릿 보고서 생성 |
| C. 코파일럿 | 기본 증거에 선택적 추가 조회와 AI 보고서를 더함 |

- 측정 지표: 필수 근거 누락률, 사실·수치 오류, 조사역 수정량, 조사역 검토·기록 시간, 툴 호출 수, 비용, 지연
- 1차 탐지의 정밀도·재현율은 조사 품질과 별개로 측정합니다.

## 6. 가정, 한계, 리스크

| 항목 | 내용 | 대응 |
|---|---|---|
| 데이터 한계 | 시뮬레이션 데이터라 실제 사기 유형의 분포와 다를 수 있습니다. | 결과를 실제 운영 효과로 일반화하지 않고, 한계를 문서에 명시합니다. |
| 비용과 지연 | LLM 호출은 비용이 들고 응답에 수십 초가 걸립니다. | 1차 탐지로 대상을 줄이고, 호출 횟수와 토큰 상한을 둡니다. |
| 비결정성 | 같은 케이스에도 에이전트의 조사 경로와 문장이 달라질 수 있습니다. | 모든 툴 호출과 결과를 기록하고, 수치 검증과 사람 검토를 거칩니다. |
| 잘못된 근거 | 모델이 툴 결과에 없는 수치나 해석을 만들 수 있습니다. | 근거 ID 연결과 수치 일치를 코드로 검증합니다. |
| 통합 리스크 | MCP 연동과 에이전트 루프는 처음 구현하는 영역입니다. | 가장 먼저 최소 구성으로 검증합니다(`05_roadmap.md`). |

## 7. 용어

| 용어 | 의미 |
|---|---|
| 케이스 | 1차 탐지된 거래 한 건에 대한 조사 단위 |
| 조사역 | 케이스를 검토하고 종결 여부를 판단하는 사람 |
| 근거 ID | 툴 결과에 포함된 증거 항목의 식별자. 보고서의 주장이 이를 참조합니다. |
| 조사 미완료 | 근거가 불충분해 보고서를 확정하지 못한 상태 |
| MCP | Model Context Protocol. LLM 애플리케이션이 외부 툴을 찾고 실행하는 방법을 표준화한 프로토콜 |
| 툴 서버 | 증거 조회 툴을 제공하는 MCP 서버 (읽기 전용) |
| 도메인 백엔드 | 케이스와 검토 이력을 관리하는 Spring Boot 서비스 |
| AI 조사 서비스 | 에이전트 루프를 실행하고 보고서를 만드는 Python 서비스 |
