## 2. 계층별 검토

### 2.1 데이터: Kaggle `kartik2112/fraud-detection` (Sparkov)

**왜 쓰는가**
- 에이전트 보고서의 가치는 "왜 의심스러운가"를 설명하는 데 있습니다. PCA로 익명화된 데이터(`V1~V28`)는 모델 성능을 겨루기에는 좋지만 설명할 거리가 없습니다. Sparkov 데이터는 가맹점명, 업종, 고객과 가맹점의 좌표, 거래 시각이 원래 형태로 있어 툴이 계산한 수치를 그대로 근거로 쓸 수 있습니다.

**트레이드오프**
| 장점 | 비용과 한계 |
|---|---|
| 해석 가능한 필드, 정답 라벨 존재 | 시뮬레이션 데이터라 실제 사기 유형 분포와 다름 |
| 약 185만 건으로 이력 조회 시나리오가 충분 | 미국 기준(USD, 미국 업종). 국내 체계와 다름 |
| 공개 데이터라 누구나 재현 가능 | `merch_lat/long`은 생성된 값이라 고객의 실제 위치로 해석하면 안 됨 |

**운영 원칙**
- 1주차는 직접 만든 소량의 합성 데이터로 시작합니다. 고액 거래, 평소 패턴과 비슷한 거래, 이력 부족 사례를 의도적으로 만들어야 툴의 경계 조건을 검증할 수 있기 때문입니다. 대용량 CSV는 4주차에 정식으로 적재합니다.
- `is_fraud`는 조사 경로에서 분리해 평가에만 씁니다(라벨 누수 방지).

### 2.2 도메인 백엔드: Spring Boot + JPA (Java 17)

**왜 쓰는가**
- 이 계층이 담당하는 일(케이스 상태 전이 `DETECTED → INVESTIGATING → REPORTED → APPROVED/REJECTED`, 조사역 판단 이력, 동시 승인 방지)은 트랜잭션 정합성이 핵심입니다. 이미 익숙한 스택이라 일정 예측이 가능하고, 면접에서 가장 깊게 설명할 수 있는 영역입니다.
- 카드사와 은행 계정계, 정보계는 Java/Spring 비중이 높아 목표 직무와의 연결이 직접적입니다.

**JPA를 쓰는 범위와 쓰지 않는 범위**
| 용도 | 방식 | 근거 |
|---|---|---|
| 케이스, 보고서, 검토 이력 | JPA 엔티티 + `@Version` 낙관적 락 | 건수가 적고 상태 변경 규칙이 중요함. 변경 감지(dirty checking)로 상태 전이 코드가 단순해짐 |
| 거래 대량 적재 | `LOAD DATA INFILE` 또는 JDBC batch | `IDENTITY` 전략에서는 insert가 즉시 실행되어 batch insert가 꺼짐. 영속성 컨텍스트에 엔티티가 계속 쌓여 메모리도 증가 |
| 룰 엔진의 집계 조회 | JPQL/네이티브 쿼리 또는 별도 조회 전용 쿼리 | 엔티티를 불러와 메모리에서 집계하면 N+1 문제와 불필요한 영속화가 생김 |

**트레이드오프**
- JPA는 상태 관리 코드를 줄여 주지만 SQL이 숨겨집니다. 룰 엔진처럼 집계가 중심인 부분은 SQL을 직접 쓰는 편이 성능과 설명 가능성 모두에서 낫습니다. "JPA를 어디에 쓰지 않았는가"를 설명할 수 있는 것도 면접 어필 포인트입니다.

**확인 사항**
- 현재 `build.gradle`은 Spring Boot 4.1.1, Java 17입니다. Boot 4.x에서 일부 스타터 이름과 모듈 구성이 바뀌었습니다(현재 `spring-boot-h2console` 등). 의존성을 추가할 때 공식 문서로 이름을 확인합니다.

### 2.3 Spring AI 의존성: 제거 권장

**현황**: `spring-ai-starter-model-anthropic`, `spring-ai-starter-model-openai`가 포함되어 있습니다.

**제거를 권하는 이유**
1. `07` 인수인계 문서의 결정에 따라 모델 호출은 Python이 담당합니다. 두 언어가 모두 모델을 호출하면 프롬프트, 툴 정의, 로그 형식이 두 곳으로 나뉩니다.
2. 스타터는 자동 설정(auto-configuration)으로 클라이언트 빈을 만들려고 하므로, API 키 프로퍼티가 없으면 애플리케이션 기동이나 테스트가 실패할 수 있습니다.
3. OpenAI 스타터는 프로젝트 범위에 없습니다.

**대안으로 남겨둘 가치**: Spring AI에는 MCP 클라이언트·서버 지원도 있습니다. 나중에 "Java 단일 언어로 통합"을 시도한다면 그때 다시 추가합니다. 지금 미리 넣어 둘 이유는 없습니다.

### 2.4 DB: MySQL

**왜 쓰는가**
- 익숙하고, 이 프로젝트의 요구(트랜잭션, 기간 조건 인덱스 조회, 읽기 전용 계정 분리)를 충분히 충족합니다.

**대안 비교**
| 대안 | 장점 | 채택하지 않는 이유 |
|---|---|---|
| PostgreSQL + PostGIS | 지리 연산을 DB에서 처리 | 거리 계산은 하버사인(Haversine) 공식으로 코드에서 충분히 해결됨. 새 DB 학습 비용 |
| Oracle | 실제 국내 금융권 표준에 가까움 | 로컬 구성이 무겁고, 포트폴리오에서 얻는 차별점이 작음 |
| SQLite (Python 쪽 1주차 실험) | 설정 없이 바로 시작 | 1주차 스파이크에는 허용. 4주차 이후에는 MySQL로 통일 |

**H2에 대한 주의**
- H2의 MySQL 호환 모드는 완전하지 않습니다(락 동작, 일부 함수, DDL 차이). 테스트가 H2에서는 통과하고 MySQL에서는 실패하는 상황을 막으려면 Testcontainers(테스트 중 Docker로 MySQL을 띄우는 라이브러리)나 Docker Compose MySQL로 테스트하는 것을 권합니다.

**권한 설계**
- MCP 서버는 읽기 전용 계정(`SELECT`만 허용)으로 접근합니다. 프롬프트를 어떻게 조작하더라도 원천 데이터를 바꿀 수 없도록 애플리케이션이 아니라 DB 권한으로 막는 것입니다.

### 2.5 툴 서버: MCP (Python, FastMCP)

**기초 개념**
- MCP(Model Context Protocol)는 LLM 애플리케이션이 외부 툴을 찾고(`tools/list`) 실행하는(`tools/call`) 방법을 JSON-RPC 메시지로 표준화한 프로토콜입니다. 툴을 제공하는 쪽이 **서버**, 서버에 연결해 호출하는 쪽이 **클라이언트**입니다.
- 전송 방식은 두 가지입니다. **stdio**는 클라이언트가 서버를 자식 프로세스로 실행하고 표준 입출력으로 통신합니다. **Streamable HTTP**는 서버가 별도 프로세스로 떠 있고 HTTP로 통신합니다.

**가장 중요한 질문: MCP가 정말 필요한가**

MCP 없이도 Python 함수를 Claude API의 `tools` 파라미터에 직접 등록하면 tool use는 동작합니다. 따라서 MCP는 "없으면 불가능한 것"이 아니며, 그 비용을 정당화할 근거가 필요합니다.

| 항목 | 함수를 직접 등록 | MCP 서버로 분리 |
|---|---|---|
| 구현량 | 적음 | 서버, 클라이언트, 전송 계층이 추가됨 |
| 디버깅 | 같은 프로세스라 쉬움 | 프로세스 경계에서 오류가 발생할 수 있음 |
| 재사용 | 해당 에이전트 전용 | 같은 서버를 Claude Code, Claude 데스크톱 앱, 다른 에이전트에서 그대로 연결 |
| 격리 | 에이전트와 DB 접근 코드가 한 프로세스 | 툴 서버만 DB 계정을 가짐. 권한 경계가 프로세스 경계와 일치 |
| 교체 가능성 | 모델 SDK에 종속 | 클라이언트(모델, 프레임워크)를 바꿔도 툴은 그대로 |

**판정: 조건부 유지**
- 유지 근거: (1) 개발 중 Claude Code에 같은 서버를 연결해 툴을 대화로 테스트할 수 있고, (2) DB 권한을 툴 서버 프로세스에만 주는 구조가 금융권의 최소 권한 원칙과 맞습니다. 이 두 가지는 이 프로젝트의 증명 목표와 직접 연결됩니다.
- 조건: 1주차에 "같은 MCP 서버를 Claude Code와 직접 만든 클라이언트 양쪽에서 호출"하는 것을 실제로 시연해야 합니다. 이것이 안 되면 MCP의 핵심 근거가 사라지므로 함수 직접 등록 방식으로 바꾸는 것을 검토합니다.

**Python을 고른 이유와 대안**
| 대안 | 장점 | 단점 |
|---|---|---|
| Python MCP SDK (채택) | 레퍼런스와 예제가 가장 많음. FastMCP로 짧게 작성 | 언어가 두 개가 됨 |
| Java (Spring AI MCP 서버) | 단일 언어, 기존 JPA 엔티티 재사용 | 처음 다루는 영역에서 참고 자료가 적어 리스크가 큼 |
| TypeScript MCP SDK | 공식 SDK가 성숙함 | 프로젝트의 다른 계층과 연결이 없음 |

가장 불확실한 영역에서는 자료가 가장 많은 쪽을 고르는 것이 리스크를 줄이는 선택입니다. Java로 옮기는 것은 MVP 완료 후 개선 과제로 둡니다.

**전송 방식 단계**
- 1~3주차: stdio. 설정이 없고 Claude Code 연결도 stdio가 가장 간단합니다.
- 5주차 이후: Spring, FastAPI와 별도 프로세스로 운영해야 하면 Streamable HTTP로 전환을 검토합니다. 툴 구현 코드는 전송 방식과 분리해 두어 전환 비용을 줄입니다.

### 2.6 에이전트: Claude Messages API + 직접 구현한 tool use 루프

**기초 개념**
- 모델은 툴을 직접 실행하지 않습니다. 요청에 툴의 이름, 설명, 입력 스키마를 함께 보내면, 모델은 필요할 때 "이 툴을 이 인자로 호출해 달라"는 `tool_use` 블록으로 응답합니다(`stop_reason: "tool_use"`).
- 애플리케이션이 인자를 검증하고 툴(MCP)을 실행한 뒤, 결과를 `tool_result` 블록으로 대화에 추가해 다시 모델을 호출합니다. 모델이 더 이상 툴을 요청하지 않으면 최종 답변으로 끝납니다. 이 "생각, 행동, 관찰" 반복을 ReAct 패턴이라고 부릅니다.
- 즉 판단은 모델이 하고, 실행 권한과 통제는 애플리케이션이 가집니다.

**왜 프레임워크 없이 직접 구현하는가**
| 대안 | 장점 | 채택하지 않는 이유 |
|---|---|---|
| 직접 루프 (채택) | 단계별 로그, 호출 상한, 타임아웃, 인자 검증을 모두 직접 통제 | 코드량이 조금 더 많음(수십~백여 줄 수준) |
| LangChain/LangGraph | 루프와 메모리를 제공 | 추상화가 두꺼워 "어떤 요청이 오갔는지" 추적이 어려움. 학습 대상이 프레임워크로 바뀜 |
| Claude Agent SDK | 툴 실행, 컨텍스트 관리 자동화 | 루프 내부를 숨기므로 감사(audit) 로그 설계를 보여주기 어려움 |
| SDK의 tool runner 헬퍼 | 루프를 대신 돌려줌 | 학습 단계에서는 원리를 가림. 직접 구현 후 비교 대상으로 검토 가능 |

금융권 관점에서 "에이전트가 무엇을 근거로 어떤 순서로 조회했는가"를 모두 재현할 수 있어야 합니다. 루프를 직접 구현해야 이 로그 구조를 자유롭게 설계할 수 있습니다.

**필수 안전장치** (상세는 `04_agent_workflow.md`에서 정의)
- 최대 반복 횟수, 툴 호출별 타임아웃, 토큰·비용 상한
- 상한에 도달하거나 툴이 실패하면 보고서를 만들지 않고 "조사 미완료"로 남김
- 화면과 로그에는 모델의 내부 추론이 아니라 툴 호출, 인자, 관찰 결과, 최종 보고서를 남김

**비용 관리**
- 개발 중 반복 호출에 비용이 들므로, 루프 로직은 응답을 흉내 내는 가짜 클라이언트(mock)로 먼저 테스트하고 실제 API 호출은 시나리오 검증에만 씁니다. 모델명은 `CLAUDE_MODEL` 환경 변수로 분리해 개발 중에는 저렴한 모델, 시연에는 상위 모델을 쓸 수 있게 합니다.

### 2.7 AI 조사 서비스 API: FastAPI (보류)

- 1~4주차에는 Python 스크립트(CLI)로 루프를 실행합니다. HTTP 계층이 없어야 문제가 생겼을 때 원인 범위가 좁아집니다.
- 5주차에 Spring의 `@TransactionalEventListener(phase = AFTER_COMMIT)`에서 조사를 요청할 때 HTTP 진입점이 필요해지면 FastAPI를 추가합니다. LLM 응답은 수십 초가 걸리므로 Spring은 요청만 보내고 즉시 반환하며(비동기), 결과는 Python이 DB에 기록하거나 콜백으로 알리는 방식을 그때 결정합니다.
- 대안: Spring이 Python CLI를 프로세스로 실행하는 방식도 가능하지만 오류 처리와 확장성이 떨어집니다.

### 2.8 Python 환경: uv + Python 3.12

- `uv.lock`으로 의존성 버전을 고정하므로 Claude, Codex, 다른 PC가 같은 환경을 재현합니다. 여러 에이전트가 협업할 때 "내 환경에서는 된다" 문제를 막는 장치입니다.
- 규칙: 의존성 추가는 `uv add`로만 하고, lock 파일 변경도 함께 커밋합니다.

### 2.9 프론트엔드: React

- 조사역 화면(케이스 목록, 툴 호출 타임라인, 근거가 연결된 보고서, 승인·반려)은 상태가 많은 UI라 컴포넌트 기반이 적합합니다.
- 위험도가 가장 낮고 일정이 밀릴 때 가장 먼저 축소합니다(로드맵 5주차 판단 지점).
- 권장 구성: Vite + TypeScript. 화면 상태가 단순하면 별도 상태 관리 라이브러리 없이 시작합니다.

## 3. 서비스 역할 구분과 상태 변경 권한

FastAPI를 붙인 Python 계층도 백엔드입니다. 다만 Spring과 책임이 다르므로 문서에서는 아래 이름으로 구분합니다.

| 계층 | 이름 | 성격 | 상태 소유 | DB 권한 |
|---|---|---|---|---|
| Spring Boot | 도메인 백엔드 (케이스·심사 서비스) | 기록 시스템(System of Record). 짧은 트랜잭션, 정합성이 핵심 | 업무 상태의 원본을 소유하고 변경 | 읽기·쓰기 |
| Python + FastAPI | AI 조사 서비스 (에이전트 오케스트레이터) | 근거를 모아 보고서 초안을 제안. 요청당 수십 초 | 소유하지 않음 (실행 중 상태만 요청 내 유지) | 없음 (결과는 Spring API로 전달) |
| MCP 서버 | 툴 서버 (읽기 전용 증거 조회) | 툴 실행 | 소유하지 않음 | 읽기 전용 계정 |

**결과 반영 방식 (잠정 결정: A)**

| 방식 | 장점 | 단점 |
|---|---|---|
| A. Python이 결과와 조사 로그를 Spring API로 보내고, Spring이 저장하고 상태를 바꿈 | 상태 변경 지점이 한 곳. 상태 전이 검증과 `@Version` 락이 한 곳에 모임. Python은 쓰기 권한 불필요 | API 호출 추가 |
| B. Python이 DB에 직접 기록 | 구현이 단순 | 두 언어가 같은 테이블에 씀. 상태 규칙 분산, 락 검증 우회 가능 |

- 조사 로그(`investigation_log`)도 A와 같은 경로로 저장합니다. 건수가 많아지면 한 번에 모아 보내는 방식을 검토합니다.
- 흐름: Spring이 커밋 후 조사를 요청하고 즉시 반환 → Python이 조사 수행 → 결과를 Spring에 콜백 → Spring이 `REPORTED`로 전이.
- 로그만 Python이 직접 쓰는 방식을 허용할지는 확인 중입니다(백엔드 역할 분리 문서의 코멘트).

## 4. 다언어 구조(Java + Python)의 전체 트레이드오프

| 비용 | 완화 방법 |
|---|---|
| 빌드, 실행, 배포 단위가 두 개 | Docker Compose로 MySQL, Spring, Python을 한 번에 실행 |
| 데이터 모델이 두 곳에 정의됨 | 계층 간 계약을 DB 스키마와 REST 명세로 한정. 스키마는 Spring(마이그레이션 도구)이 단독 소유 |
| 디버깅 범위 확대 | 공통 식별자(`case_id`, `trace_id`)를 양쪽 로그에 기록 |

얻는 것: 익숙한 영역(Java)과 새로 익히는 영역(Python 에이전트)이 분리되어, 학습 리스크가 한 곳에 모이고 막혔을 때 영향 범위가 제한됩니다.

## 6. 면접 어필 포인트

- "MCP를 쓴 이유"를 유행이 아니라 **재사용성과 권한 경계**로 설명하고, 직접 함수 등록 방식과 비교한 근거를 제시할 수 있습니다.
- 프레임워크 대신 tool use 루프를 직접 구현한 이유를 **감사 추적 가능성**으로 설명할 수 있습니다.
- 상태를 소유하는 도메인 백엔드와 상태 없이 근거를 만드는 AI 조사 서비스를 분리하고, AI 쪽에는 쓰기 권한을 주지 않은 구조로 통제 관점을 설명할 수 있습니다.
- JPA를 쓰지 않은 영역(대량 적재, 집계)을 명확히 구분한 점이 ORM의 내부 동작 이해를 보여줍니다.
