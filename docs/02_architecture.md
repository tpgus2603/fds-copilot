# 02. 아키텍처 (Architecture)

## 1. 전체 구성

```
[Kaggle CSV]
     │  (배치 적재)
     ▼
┌──────────────┐     ┌─────────────────────────┐
│   MySQL      │◀────│ Spring Boot 백엔드        │
│ 거래/케이스/로그│     │ - 룰 엔진 (1차 탐지)       │
└──────────────┘     │ - 케이스 관리 REST API     │
     ▲               │ - 승인/반려 처리           │
     │               └───────────┬─────────────┘
     │ (조회 전용)                 │ 케이스 생성 시 조사 요청
     │                           ▼
┌──────────────┐     ┌─────────────────────────┐
│  MCP 서버      │◀───▶│ FastAPI 오케스트레이터     │
│ 1. 거래 이력    │ MCP │ - Claude API 호출         │
│ 2. 가맹점 리스크 │     │ - ReAct 루프 제어          │
│ 3. 지리 이상치  │     │ - 추론 로그 기록/보고서 생성 │
└──────────────┘     └───────────┬─────────────┘
                                 │ Claude API (tool use)
                                 ▼
                           [Claude 모델]

┌─────────────────────────────────────────────┐
│ React 대시보드: 케이스 목록, 추론 로그 타임라인, 승인/반려 │
└─────────────────────────────────────────────┘
```

## 2. 계층별 책임

### 2.1 데이터 계층 (MySQL)
- 거래 원천 데이터, 조사 케이스, 에이전트 추론 로그, 보고서, 조사역 판단 이력을 저장합니다.
- MCP 서버는 **읽기 전용 계정**으로 접근합니다. 에이전트가 어떤 추론을 하더라도 원천 데이터를 변경할 수 없도록 권한 수준에서 차단하기 위함입니다.

### 2.2 백엔드 계층 (Spring Boot + JPA)
- **룰 엔진**: 고액, 심야 시간대, 짧은 시간 내 연속 거래, 거주지와 가맹점 간 원거리 등 설명 가능한 규칙으로 1차 탐지합니다.
- **케이스 상태 관리**: `DETECTED → INVESTIGATING → REPORTED → APPROVED/REJECTED`
  - 상태 전이는 단일 트랜잭션 안에서 검증 후 수행합니다.
  - 동일 케이스에 대한 중복 승인을 막기 위해 `@Version` 기반 낙관적 락을 사용합니다. 조사역 동시 처리 빈도가 낮아 비관적 락의 대기 비용이 불필요하기 때문입니다.
- **조사 요청 트리거**: 케이스 커밋 이후 오케스트레이터를 호출합니다.
  - `@TransactionalEventListener(phase = AFTER_COMMIT)`를 사용합니다. 트랜잭션 내부에서 외부 HTTP를 호출하면, 롤백된 케이스에 대해 조사가 시작되거나 커넥션을 LLM 응답 시간 동안 점유하는 문제가 생기기 때문입니다.

### 2.3 MCP 서버 계층
**MCP(Model Context Protocol) 기초 개념**
- MCP는 LLM 애플리케이션이 외부 도구와 데이터에 접근하는 방식을 표준화한 프로토콜입니다. JDBC가 DB 벤더별 차이를 인터페이스로 감추듯, MCP는 "툴 목록 제공(`tools/list`)"과 "툴 실행(`tools/call`)"을 표준 메시지(JSON-RPC)로 정의합니다.
- 구성 요소: **MCP 서버**(툴 제공자, 본 프로젝트에서 직접 구현), **MCP 클라이언트**(서버에 연결하는 쪽, 오케스트레이터 내부), **호스트**(클라이언트를 품은 애플리케이션).
- 장점: 동일 MCP 서버를 FastAPI 오케스트레이터뿐 아니라 Claude Code, Claude 데스크톱 앱에서도 그대로 연결해 테스트할 수 있습니다. 이것이 "개발 워크플로 통합"을 증명하는 지점입니다.

**툴 3종** (입출력 스키마는 03_mcp_tool_spec.md에서 정의)
| 툴 | 역할 |
|---|---|
| 거래 이력 조회 | 카드 기준 최근 N일 거래, 평균 금액, 이용 업종 분포 |
| 가맹점 리스크 조회 | 가맹점/업종의 과거 이상거래 비중 등 리스크 지표 |
| 지리적 이상치 계산 | 거주지-가맹점 거리, 직전 거래 대비 이동 속도(불가능 이동 판정) |

### 2.4 AI 오케스트레이션 계층 (FastAPI + Claude API)
**Tool use 기초 개념**
- Claude 모델은 직접 DB에 접근하지 않습니다. 요청 시 "사용 가능한 툴의 이름·설명·입력 스키마"를 함께 보내면, 모델은 답변 대신 "이 툴을 이 인자로 호출해 달라"는 `tool_use` 블록을 반환할 수 있습니다.
- 실제 실행은 **우리 코드**가 수행하고, 결과를 `tool_result`로 다시 모델에 전달합니다. 즉 모델은 판단만, 실행 권한은 애플리케이션이 가집니다.

**ReAct 루프 개요** (상세는 04_agent_workflow.md)
1. 케이스 정보와 툴 목록을 담아 Claude 호출
2. 응답이 `tool_use`이면 MCP 클라이언트로 해당 툴 실행 → 결과를 대화에 추가 → 1로 복귀
3. 응답이 최종 텍스트이면 보고서로 저장하고 종료
4. 안전장치: 최대 반복 횟수, 툴 호출 타임아웃, 토큰 예산 상한

**오케스트레이터를 Python으로 분리한 근거**
- MCP·Claude SDK의 레퍼런스와 예제가 Python 중심이어서 가장 리스크가 큰 영역의 학습 비용을 줄입니다.
- LLM 호출은 수십 초 단위의 I/O 대기이므로 비동기 처리(asyncio)가 자연스러운 FastAPI가 적합합니다.
- 트레이드오프: 언어가 두 개가 되어 운영 복잡도가 증가합니다. 계층 간 계약을 REST와 DB 스키마로 한정하여 결합도를 낮춥니다.

### 2.5 프론트엔드 계층 (React)
- 케이스 목록과 상태 필터
- 추론 로그 타임라인: 각 단계의 사고(Reasoning), 호출한 툴과 인자, 관찰 결과를 순서대로 표시
- 보고서 뷰: 각 주장 옆에 근거가 된 툴 호출 단계 링크
- 승인/반려 및 사유 입력

## 3. 핵심 데이터 흐름
1. 배치가 거래를 적재하고 룰 엔진이 탐지하여 `fraud_case`를 생성합니다.
2. 커밋 후 이벤트로 오케스트레이터에 조사를 요청합니다.
3. 오케스트레이터가 ReAct 루프를 수행하며 각 단계를 `investigation_log`에 기록합니다.
4. 최종 보고서를 `investigation_report`에 저장하고 케이스를 `REPORTED`로 전이합니다.
5. 조사역이 대시보드에서 승인 또는 반려합니다.

## 4. 설계 원칙 요약
| 원칙 | 구현 |
|---|---|
| 최소 권한 | MCP는 읽기 전용, 상태 변경은 백엔드만 수행 |
| 추적 가능성 | 모든 툴 호출과 모델 응답을 로그로 영속화 |
| 사람의 최종 결정 | 에이전트는 판정이 아닌 권고만 산출 |
| 장애 격리 | 에이전트 실패 시 케이스는 `DETECTED`로 남아 수동 조사 가능 |

## 5. 면접 어필 포인트
- "외부 LLM 호출을 트랜잭션 밖으로 분리하고, 에이전트에는 읽기 권한만 부여했다"는 설명은 금융권 안정성·통제 관점을 보여줍니다.
