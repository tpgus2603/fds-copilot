# 02. 아키텍처 (Architecture)

## 1. 전체 구성

```
[Kaggle CSV / 합성 데이터]
        │ (배치 적재)
        ▼
┌────────────────────┐   읽기·쓰기   ┌──────────────────────────────┐
│       MySQL         │◀────────────│ 도메인 백엔드 (Spring Boot)     │
│ 거래 / 케이스 /       │             │ - 규칙 엔진 (1차 탐지)          │
│ 조사 기록 / 보고서     │             │ - 케이스 상태 관리, 검토 이력     │
└────────────────────┘             │ - REST API                    │
        ▲                          └──────┬───────────────▲───────┘
        │ 읽기 전용 계정                    │ ① 조사 요청      │ ③ 결과·기록 전달
        │                                 ▼                │
┌────────────────────┐   MCP     ┌──────────────────────────────┐
│ 툴 서버 (MCP)        │◀─────────▶│ AI 조사 서비스 (Python)         │
│ - 거래 이력 조회      │  (stdio)  │ - 조사 루프 제어 (tool use)      │
│ - 가맹점·업종 지표    │           │ - 보고서 생성, 근거 검증          │
│ - 지리적 이상치 계산   │           └──────────────┬───────────────┘
└────────────────────┘                          │ ② Claude API
                                                ▼
                                          [Claude 모델]

┌──────────────────────────────────────────────────────────────┐
│ 검토 화면 (React): 케이스 목록, 툴 호출 타임라인, 보고서, 종결 처리   │
└──────────────────────────────────────────────────────────────┘
```

## 2. 구성 요소별 책임

| 구성 요소 | 책임 | 상태 소유 | DB 권한 |
|---|---|---|---|
| 도메인 백엔드 (Spring Boot + JPA) | 규칙 탐지, 케이스 상태 전이, 조사 기록·보고서 저장, 조사역 검토 이력 | 업무 상태의 원본을 소유 | 읽기·쓰기 |
| AI 조사 서비스 (Python) | 조사 루프 실행, 보고서 초안 생성, 근거 ID·수치 검증 | 소유하지 않음 (실행 중 상태만 요청 안에서 유지) | 없음 |
| 툴 서버 (Python MCP) | 증거 조회와 지표 계산 | 소유하지 않음 | 읽기 전용 |
| 검토 화면 (React) | 조사역의 조회와 종결 입력 | 소유하지 않음 | 없음 (백엔드 API 사용) |

업무 상태를 바꾸는 곳을 도메인 백엔드 한 곳으로 제한합니다. 이렇게 하면 상태 전이 검증과 동시성 제어가 한 곳에 모이고, AI 쪽 구성 요소는 어떤 출력을 내더라도 데이터를 직접 바꿀 수 없습니다.

### 2.1 데이터 (MySQL)

- 거래 원천 데이터, 조사 케이스, 조사 기록(툴 호출과 결과), 보고서, 조사역 검토 이력을 저장합니다.
- 툴 서버는 `SELECT`만 허용된 계정으로 접근합니다. 프롬프트가 어떻게 조작되더라도 원천 데이터를 바꿀 수 없도록 애플리케이션이 아니라 DB 권한으로 막습니다.
- 정답 라벨은 별도 평가 테이블에 두고 툴 서버 계정에는 조회 권한을 주지 않습니다.

### 2.2 도메인 백엔드 (Spring Boot + JPA)

**규칙 엔진**: 고액, 심야 시간대, 단시간 연속 거래, 거주지와 가맹점 간 원거리 등 설명 가능한 규칙으로 1차 탐지합니다. 집계가 중심이므로 엔티티를 불러와 메모리에서 계산하지 않고 SQL로 처리합니다.

**케이스 상태**

```
DETECTED ──▶ INVESTIGATING ──▶ REPORTED ──▶ CLOSED_FRAUD   (사기 확정)
                  │                 │   └──▶ CLOSED_NORMAL  (정상 종결)
                  │                 └──────▶ REINVESTIGATE ──▶ INVESTIGATING
                  └──▶ INCOMPLETE (조사 미완료: 툴 실패, 호출 상한, 근거 부족)
                           └──▶ 조사역 수동 조사 또는 재조사 요청
```

- 상태 전이는 허용된 전이인지 검증한 뒤 단일 트랜잭션에서 수행합니다.
- 같은 케이스를 두 조사역이 동시에 종결하는 것을 막기 위해 `@Version` 낙관적 락을 사용합니다. 동시 처리 빈도가 낮아 비관적 락의 대기 비용이 불필요하기 때문입니다.
- 조사역의 결정은 케이스에 대한 판단이며, 보고서를 "승인"하는 것이 아닙니다. 보고서는 판단을 돕는 자료입니다.

**조사 요청**: 케이스가 커밋된 뒤 `@TransactionalEventListener(phase = AFTER_COMMIT)`로 AI 조사 서비스에 요청합니다. 트랜잭션 안에서 외부 호출을 하면 롤백된 케이스에 대해 조사가 시작되거나, LLM 응답을 기다리는 수십 초 동안 DB 커넥션을 점유하기 때문입니다. 요청은 비동기로 보내고 즉시 반환합니다.

### 2.3 툴 서버 (MCP)

**MCP 기초**
- MCP(Model Context Protocol)는 LLM 애플리케이션이 외부 툴을 찾고(`tools/list`) 실행하는(`tools/call`) 방법을 JSON-RPC 메시지로 표준화한 프로토콜입니다. JDBC가 DB 벤더별 차이를 인터페이스 뒤로 감추듯, MCP는 툴 제공자와 사용자 사이의 형식을 통일합니다.
- 툴을 제공하는 쪽이 **서버**, 서버에 연결해 호출하는 쪽이 **클라이언트**, 클라이언트를 포함한 애플리케이션이 **호스트**입니다. 이 프로젝트에서는 툴 서버를 직접 구현하고, AI 조사 서비스가 클라이언트를 포함합니다.
- 같은 툴 서버를 개발 중에는 Claude Code에 연결해 대화로 테스트하고, 운영 흐름에서는 AI 조사 서비스가 호출합니다.

**툴 3종** (입출력 스키마는 `03_mcp_tool_spec.md`에서 정의)

| 툴 | 역할 | 주의 |
|---|---|---|
| 거래 이력 조회 | 대상 거래 시점 이전의 카드별 거래, 평균 금액, 업종 분포 | 대상 거래 자체와 이후 거래는 제외 |
| 가맹점·업종 지표 | 가맹점과 업종의 과거 탐지 비중 등 참고 지표 | 실제 사기율로 표현하지 않음 |
| 지리적 이상치 계산 | 거주지와 가맹점 간 거리, 직전 거래 대비 이동 속도 | 가맹점 좌표를 고객의 실측 위치로 해석하지 않음 |

**툴 결과의 공통 형식**: 모든 결과에 기준 시점, 조회 기간, 표본 수, 근거 ID를 포함합니다. 결과가 없는 경우(`empty`)와 조회 실패(`error`)를 다른 형식으로 구분합니다.

**전송 방식**: 처음에는 stdio(클라이언트가 서버를 자식 프로세스로 실행하고 표준 입출력으로 통신)를 사용합니다. 서비스를 별도 프로세스로 운영해야 할 때 Streamable HTTP로 전환을 검토합니다.

### 2.4 AI 조사 서비스 (Python + Claude API)

**Tool use 기초**
- 모델은 DB나 툴을 직접 실행하지 않습니다. 요청에 툴의 이름, 설명, 입력 스키마를 함께 보내면, 모델은 필요할 때 "이 툴을 이 인자로 호출해 달라"는 `tool_use` 블록으로 응답합니다.
- 애플리케이션이 인자를 검증하고 툴을 실행한 뒤, 결과를 `tool_result` 블록으로 대화에 추가해 다시 모델을 호출합니다. 판단은 모델이, 실행 권한과 통제는 애플리케이션이 가집니다.

**조사 루프** (상세는 `04_agent_workflow.md`)
1. 케이스 정보와 기본 증거, 사용 가능한 툴 목록을 담아 모델을 호출합니다.
2. 응답이 `tool_use`이면 인자를 검증하고 MCP로 툴을 실행한 뒤 결과를 추가하고 1로 돌아갑니다.
3. 응답이 최종 보고서이면 근거 ID 연결과 수치 일치를 검증합니다.
4. 검증을 통과하면 보고서를, 실패하거나 상한에 도달하면 "조사 미완료"와 사유를 도메인 백엔드에 전달합니다.

안전장치: 최대 반복 횟수, 툴 호출별 타임아웃, 토큰·비용 상한.

**구현 단계**: 처음에는 CLI로 실행합니다. 도메인 백엔드와 연결하는 단계에서 FastAPI로 HTTP 진입점을 추가합니다.

**Python으로 분리한 근거**
- MCP와 Claude SDK의 레퍼런스가 Python 중심이어서 가장 불확실한 영역의 구현 리스크를 줄입니다.
- LLM 호출은 수십 초 단위의 I/O 대기이므로 asyncio 기반 처리가 적합합니다.
- 트레이드오프: 언어가 두 개가 되어 운영 복잡도가 늘어납니다. 계층 간 계약을 REST API와 `contracts/`의 스키마로 한정하고, DB 스키마는 도메인 백엔드가 단독으로 소유합니다.

### 2.5 검토 화면 (React)

- 케이스 목록과 상태 필터
- 툴 호출 타임라인: 호출한 툴, 인자, 결과를 순서대로 표시합니다. 모델의 내부 추론은 표시하지 않습니다. 검증할 수 있는 것은 툴 호출과 결과이기 때문입니다.
- 보고서 뷰: 의심 근거, 반대 근거, 정보 부족을 구분해 보여주고, 각 주장에서 근거가 된 툴 결과로 이동할 수 있습니다.
- 종결 처리: 사기 확정, 정상 종결, 재조사 요청과 사유 입력

## 3. 핵심 데이터 흐름

1. 배치가 거래를 적재하고 규칙 엔진이 탐지해 케이스(`DETECTED`)를 만듭니다.
2. 커밋 후 이벤트로 AI 조사 서비스에 조사를 요청하고, 케이스를 `INVESTIGATING`으로 바꿉니다.
3. AI 조사 서비스가 조사 루프를 실행합니다. 툴 서버는 읽기 전용 계정으로 증거를 조회합니다.
4. AI 조사 서비스가 보고서와 조사 기록을 도메인 백엔드 API로 전달합니다. 도메인 백엔드가 저장하고 케이스를 `REPORTED` 또는 `INCOMPLETE`로 바꿉니다.
5. 조사역이 검토 화면에서 케이스를 종결하거나 재조사를 요청합니다.

## 4. 장애 처리

| 상황 | 처리 |
|---|---|
| AI 조사 서비스 무응답 | 일정 시간 후 도메인 백엔드가 케이스를 `INCOMPLETE`로 바꾸고 수동 조사가 가능하게 합니다. |
| 툴 조회 실패 | 실패를 기록하고, 필수 근거가 없으면 보고서를 만들지 않습니다. |
| 보고서 검증 실패 | 보고서를 폐기하고 `INCOMPLETE`와 실패 사유를 남깁니다. |
| 중복 결과 전달 | 조사 요청 ID 기준으로 멱등 처리해 같은 결과가 두 번 저장되지 않게 합니다. |

## 5. 미결정 사항

- 조사 기록(툴 호출별 로그)을 결과와 함께 한 번에 전달할지, 단계마다 전달할지
- AI 조사 서비스의 결과 전달 방식: 콜백 API 호출과 메시지 큐 중 선택 (초기에는 콜백 API)
- 테스트 환경의 DB: MySQL 컨테이너(Testcontainers) 사용 여부
