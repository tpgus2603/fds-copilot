## 결정 변경
- 기본 증거(거래 이력 90일)는 코드가 결정적으로 수집하고, 모델은 추가 조회와 보고서를 담당 (평가 B/C안의 공정한 비교 기준)
- 최종 보고서는 `submit_report` 툴 호출로 받고, 같은 스키마로 다시 검증
- 조사 범위: 실행마다 툴 서버를 새로 띄워 대상 거래 하나로 고정 (#15 질문, 03 명세 남은 질문 해소)
- 근거 전역 참조: `<run_id>/<evidence_id>#<JSON Pointer>`
- 보고서 검증 실패 시 재요청하지 않고 미완료로 기록 (평가 왜곡 방지, 6주차 재검토)
- 툴 재시도는 `retryable`일 때 조사 서비스가 1회만, 병렬 툴 실행 없음
- 내부 추론(extended thinking) 미사용
- (리뷰 반영) 보고서 문장에 숫자 금지, `{0}` 자리표시자로 근거를 가리키고 서버가 렌더링 카탈로그로 채움. "평균 결제 금액은 5달러" + 거래 건수 5 인용처럼 다른 필드 값을 다른 의미로 쓰는 경우를 숫자 비교로는 막을 수 없었음
- (리뷰 반영) 권고와 발견 사항의 정합성: 추가 검토 권고는 suspicion, 특이점 없음은 counter 필수. 근거 없는 gap만 있으면 근거 부족만 가능
- (리뷰 반영) `submit_report`는 응답의 유일한 툴 호출. 혼합·중복 제출은 거부하고 루프 계속 (거부도 툴 호출 1회로 셈)
- (리뷰 반영) 상한은 논리 호출로 세고 실제 시도를 따로 기록, 입력 토큰 예산은 요청 전 확인, 시간 제한은 단일 마감 시각
- (재리뷰 반영) V1 숫자 금지를 유니코드 숫자 범주(Nd, Nl, No) 전체로 확장. JSON Schema 정규식은 구현마다 유니코드 범주 지원이 달라 ASCII만 막을 수 있으므로, 최종 판정은 `report_rules.numeric_chars`
- (재리뷰 반영) V4는 JSON 타입을 먼저 비교 (Python의 `False == 0` 차단), 숫자끼리는 10진수 비교. 기준 구현 `report_rules.json_values_equal`
- (재리뷰 반영) 입력 토큰 상한: `spent + count_tokens(다음 요청 전체) × 1.05 ≤ 60,000`을 요청 전에 확인. 첫 요청 포함, 실패한 시도는 누적에서 제외, 산정 실패 시 요청하지 않음
- (재리뷰 반영) 조회 툴 한도는 실행 허가 수로 셈. 한 응답의 조회 요청이 남은 한도를 넘으면 그 응답의 조회 전체 거부. 기본 증거와 제출은 제외
- (재리뷰 반영) 표본 수 충족은 `gap`, `counter`는 실제 정상 정황만. T2 기반 counter 예시 추가
- (리뷰 반영) 기본 증거의 `empty`·`insufficient`는 정상 진행, 평가는 첫 제출 통과율과 미완료율을 함께 집계

## 구현 결정 (#15)
- 재시도는 SDK(`max_retries`)가 아니라 `AnthropicModelClient`가 직접 수행. 논리 호출과 실제 시도 수를 구분해 기록하기 위해서
- 모델 호출과 토큰 산정을 루프에서 `asyncio.wait_for`로 감싸 단일 마감 시각을 강제. 클라이언트 구현이 멈춰도 `TIME_LIMIT`으로 끝남
- 툴 서버 자식 프로세스에는 `FDS_*`, `ANTHROPIC_*` 환경 변수를 넘기지 않음 (키가 툴 서버로 가지 않게)
- 렌더링은 툴이 준 값을 다시 반올림하지 않고 그대로 표시 (예: 비율 20.23)
- anthropic SDK 2.x는 `httpx`가 아니라 `httpx2`를 사용. 가짜 전송 계층 테스트는 `httpx2.MockTransport`
- 평가 세트 v0은 #26으로 분리 (실제 모델 실행이 필요해 사람이 실행)
- CI 경로의 `data/fixtures/**` 중복 항목 정리 (#23·#25 병합 결과)
